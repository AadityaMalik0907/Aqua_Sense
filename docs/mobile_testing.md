# AquaSense Mobile Network Resiliency & Disconnection Specification

> **Architectural Scope Note**: AquaSense currently provides a responsive Oceanic Glassmorphic Web Dashboard and a Python FastAPI backend service. The following specification defines the mandatory architectural behavior, fault-tolerance protocols, and state reconciliation rules for native mobile client applications (Android/iOS) when client-to-device Wi-Fi drops during telemetry operations.

---

### Mobile Client Behavior During In-Flight Wi-Fi Disconnection

When a mobile application loses Wi-Fi connectivity during an ongoing operation—detected immediately via platform network listeners (Android `ConnectivityManager.NetworkCallback` or iOS `NWPathMonitor`) alongside transport socket timeouts—the app must instantly display a non-blocking, high-visibility connection-lost banner (*"Wi-Fi connection lost · Operating in offline mode"*) while retaining last-known telemetry on screen instead of clearing metrics or resetting levels to zero. The client immediately marks the displayed readings with an amber "Cached / Stale" indicator, stops the live pulse animation, and temporarily disables write actions to prevent conflicting operator inputs. Concurrently, a background retry manager initiates an automated reconnection loop using exponential backoff with randomized jitter (e.g., retrying after 1s, 2s, 4s, 8s, up to a 30s ceiling) to conserve device battery and avoid network-storming the gateway. As soon as network reconnection is confirmed, the mobile client performs an authoritative state reconciliation handshake by fetching fresh device status (`GET /device/{id}/status`) and latest tank telemetry (`GET /api/tank/summary`) to verify actual physical hardware status before resuming normal operations. Furthermore, to avoid duplicate operations if device-control actions (such as pump toggles or emergency shutoff valves) are supported, each command payload must carry a unique cryptographic idempotency key (UUIDv4); upon reconnection, the backend checks this idempotency key against recent execution logs and safely rejects duplicate requests if the physical hardware already executed the action prior to the Wi-Fi drop.
