# AquaSense Mobile Network Resiliency & Disconnection Specification

When the AquaSense mobile application detects a Wi-Fi disconnection during an ongoing operation—identified instantaneously through native operating system network state listeners (such as Android's `ConnectivityManager` or iOS's `NWPathMonitor`) combined with socket heartbeat timeouts—the client must immediately surface a clear, non-intrusive status banner (e.g., *"Connection lost · Attempting to reconnect..."*) to inform the user while temporarily disabling interactive write triggers to prevent ambiguous user input. Concurrently, any in-flight asynchronous operations, such as valve controls or threshold modifications, must be preserved in a local, encrypted SQLite/Room offline queue accompanied by a unique cryptographic idempotency key (UUIDv4) and timestamp rather than being discarded or repeatedly fired blindly. The mobile client initiates a controlled background retry mechanism utilizing exponential backoff with randomized jitter (e.g., retrying after 2s, 4s, 8s, up to a maximum threshold) to conserve device battery and avoid connection storms. Upon successful network re-establishment, the application immediately performs an authoritative telemetry handshake by requesting the latest device status (`GET /device/{id}/status`) and reservoir readings (`GET /api/tank/summary`) to reconcile the client's cached UI state against physical reality before processing any pending actions. Finally, to prevent duplicate commands or hazardous double-actuation of physical pumps and intake valves, each queued request is replayed against the backend using its original idempotency token; if the server-side audit log indicates that the physical tank controller already processed the command prior to the Wi-Fi drop, the transaction is marked as resolved and safely deduplicated without re-triggering physical hardware.
